Day 1 · dx_9487, and why a bag of codes fails¶

The problem. IRIX Dx code dx_9487 (Atypical Chest Pain) currently routes every case to manual review at RUW. It maps to five nonspecific ICD-10 codes:

Code Meaning Share of dx_9487
R07.89 Other chest pain 48.1%
R07.9 Chest pain, unspecified 42.5%
R07.2 Precordial pain 6.5%
R07.8 Other chest pain 1.8%
R07.82 Intercostal pain 1.1%

Every one of these is ambiguous by construction — "chest pain" can mean a real cardiac issue or a benign cause (musculoskeletal, GI, anxiety/panic). The code alone doesn't say which, so every case currently gets manual review, which is costly and slow.

Today's goal: get the OMOP extract for this cohort loaded as one event stream, understand the four preprocessing decisions baked into it, and see the exact failure that motivates the rest of the week.

The working hypothesis (to test, not assume): a meaningful share of dx_9487 cases are anxiety/panic presentations coded as chest pain. If true, comorbid anxiety/panic Dx and SSRI/benzodiazepine Rx codes should associate strongly with dx_9487. The analysis has to be built so the data can show something else instead — GERD, costochondritis, or genuine cardiac workup — not just confirm the story going in.

Summary¶

Every unsupervised method is a distance function plus a search procedure. Changing the representation moves the answer more than changing the algorithm does, so the leverage is upstream. Today is the upstream.

Three things that all get called "pattern"¶

Term What it is Built on Auditable?
Cluster a group of similar patients Day 2 partly
Motif a recurring ordered subsequence Day 3 yes
Embedding a direction in a learned space Day 4 no

Deciding which of these is the actual deliverable for the dx_9487 triage decision is the single most important scoping question on this project.

Technique chosen per subtopic¶

Subtopic We use Mentioned only
Similarity cosine on binary codes Jaccard, Dice, Gower, Mahalanobis

Parts-based NMF archetypal analysis, sparse PCA
Non-linear view t-SNE (ships with sklearn) UMAP — better, pip install umap-learn

0 · Getting the data¶

ethos_omop.extract_cohort() pulls the dx_9487 cohort: any patient carrying one of the five R07.x codes, defined in sql/chest_pain_cohort.sql. It dumps the same shape extract_omop() does — master_* as the source of truth, ethos_dip excluded on both concept_id and source_concept_id for every domain table, standard-named symlinks for meds_etl_omop, plus:

  • concept.csv slimmed to the concept_ids the cohort actually references, instead of the full multi-million-row table.
  • concept_ancestor dumped too, restricted to rows touching the cohort — needed for ontology rollup (unspecified chest-pain codes to their parents, drugs to ingredients).
import ethos_omop as eo
eo.extract_cohort("../sql/chest_pain_cohort.sql")   # -> ../data_input/

The next cell runs this once (150,368 patients, all real Ethos production data) and skips it on every re-run once ../data_input/ exists.

Without Snowflake, or when you want data whose answer you already know:

python make_demo_extract.py 2000

The demo extract has the same schema — integer concept_ids resolved through concept.csv, master_* table names, the symlinks — plus a truth.csv giving each patient's planted trajectory archetype. Real extracts have no truth.csv. That absence is the whole problem this course is about, and every notebook here works either way.

1 · Four decisions¶

Read these before trusting anything downstream. Each is a modelling choice, not a detail.

1. Standard concepts only. load_events() keeps standard_concept == 'S' and drops concept_id = 0 (unmapped). Note the exclusion idiom in the extract is IS DISTINCT FROM 'ethos_dip', not <> 'ethos_dip' — the latter silently drops NULLs.

2. concept_code stays a string. Never let pandas parse it as numeric; leading zeros and alphanumeric codes both break.

3. Claims carry a DATE, not a timestamp. Same-day events have no true order. DOMAIN_ORDER breaks ties deterministically — visit, then condition, procedure, measurement, drug, observation. It is arbitrary and it is written down. Stanford's CLMBR was built for minute-level resolution; we do not have that, and pretending otherwise is where silent errors come from.

4. There is no observation_period in the extract. observation_window() derives a proxy from first and last observed event, which understates the true window. Anyone whose history starts near their first event is left-truncated: "no prior diagnosis" may mean "not observed yet."

That is the motivation for the whole week. Near-identical features, opposite triage answer. The information lives in the order and the surrounding evidence, and a flat bag of codes throws both away.

This is not a modelling failure. No estimator can recover something the input does not contain.

On chest_pain_labels()¶

There is no adjudicated ground truth for "was this actually cardiac." chest_pain_labels() builds probe labels from corroborating co-evidence only — anxiety/panic diagnoses, SSRIs, or benzodiazepines on the psych side; troponin, stress tests, coronary angiography, or a CAD diagnosis on the cardiac side. Patients with both kinds of evidence, or neither, are dropped, and the counts are printed so you can see how many.

The time order is deliberately not used here. If you labelled by "anxiety dx before chest pain code" and then tested whether the order predicts the label, you'd get perfect accuracy by construction and learn nothing. Days 3-4 test order directly — the label has to stay independent of it, or the test is circular.

Rule of thumb for claims: use cosine on binary or count code vectors. Euclidean punishes patients simply for having long histories, so the distance ends up driven by utilisation volume rather than clinical content — which in your data is partly a function of what got ordered during underwriting.

5 · The curse of dimensionality¶

On the full Ethos vocabulary you will have tens of thousands of columns, not the few dozen here. At that width every pair of patients becomes equidistant and "nearest neighbour" stops meaning anything.

On the demo extract, look at where DM_STABLE and DM_PROGRESSIVE land. They overlap heavily, because their code sets are nearly identical — the only difference is that one adds GLP-1 and insulin later. Day 3 separates them cleanly.

Three things never to claim from a t-SNE or UMAP plot¶

  1. Cluster sizes are meaningful. They are not.
  2. Distances between clusters are meaningful. They are not.
  3. Apparent density is meaningful. It is a function of perplexity.

Never cluster on the 2-D output. Cluster in SVD space; use the projection only to look.

def describe(ids):
    n = len(ids)
    if n == 0:
        return {'N (%)': '0 (0.0)'}
    row = {'N (%)': f"{n} ({n / len(cp_ids) * 100:.1f})"}
    a_yrs = age_yrs.reindex(ids)
    row['Age, mean (SD)'] = f"{a_yrs.mean():.1f} ({a_yrs.std():.1f})"
    row['Female, %'] = f"{(gender.reindex(ids) == 'FEMALE').mean() * 100:.1f}"
    lb = win_idx.reindex(ids)
    row['Lookback days, median (IQR)'] = (
        f"{lb.median():.0f} ({lb.quantile(.25):.0f}-{lb.quantile(.75):.0f})")
    for t in CODE_ROWS:
        row[f'{t}, %'] = f"{len(has[t] & ids) / n * 100:.1f}"
    for k in range(8):
        row[f'NMF component {k}, %'] = f"{(dom_component.reindex(ids) == k).mean() * 100:.1f}"
    return row
